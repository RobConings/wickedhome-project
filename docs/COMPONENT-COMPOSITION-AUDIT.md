## Changes and ownership

- Screens now compose Stack, Inline, PageGrid, PageSection, Card, Text and domain components. Existing responsive breakpoints, IDs, refs and event handlers remain with their owning feature.
- Text centralizes body-copy size, tone and weight while inheriting surrounding styles by default. Layout primitives expose the spacing already used by the app, including stretch alignment and explicit zero grid gap.
- CardHeading keeps supporting copy below its title inside CardHeader, leaving the other header column for actions. Twenty repeated label/control/help groups now use FormField, including its accessible description wiring; standard two-column form sections use FormGrid.
- GeneralList has an embedded variant for related records inside cards. It shares list semantics, keys and loading/error/empty states without duplicating the search toolbar, view selector or card surface. Ordinary detail lists use this variant.
- DescriptionList/DescriptionItem handle property groups, including horizontal label/value rows. Masonry and CanvasOverlay own the remaining reusable column and map positioning rules.
- Xtra and Collect&Go use the same retailer account-access editor and normal-browser import UI. Each integration retains its own parser, API calls, permission checks and credential handling.
- CookingIngredientsTray and SessionItemForm own their mobile sheet and interactive shopping-row behavior, respectively.

## Native markup reviewed

Native HTML is expected inside primitives and compositions. An h2, button, anchor, input, svg, dt/dd or list item has semantic meaning; replacing every tag with a generic Box would not improve reuse. Lower-layer Card, SectionHeader, FormField and state components own their markup and styling.

Remaining screen lists are domain interactions: stock adjustment rows and warnings, shopping requirement/checklist rows, recipe ingredients and ordered cooking steps, and financial allocation breakdowns. Their rows have feature-specific actions or ordering, rather than a second ordinary list implementation. They continue to use their feature components. Native forms remain in the account-link verification and shopping session planning/receipt workflows; those depend on verification navigation, grouped selections, file upload, acquisition matching and stock-count decisions. They are explicit domain-form exceptions to GeneralForm, not templates for new ordinary forms. The device-profile editor and home-automation configuration retain their conditional domain editors.

This structural audit does not prove runtime permissions, remote API availability or every visual state. Lint enforces layer imports and screen composition; the browser checks exercise responsive layouts and representative interactions. No server behavior or schema is changed by this refactor.
